## Request
- **Verbatim**: "a 'why did you do that' trail on any bot action — the tool calls behind a message, one click."
- **Requester**: plink
- **Origin**: backlog #17 (2026-08-28)

## Problem
A resident's reply arrives as finished prose. What it read, searched, remembered or changed to get there is visible only in host logs (Gable's `gable.log`, Claudette's `disjorn_bot.log`) and the broker audit. A person who wonders "where did that come from?" has no way to ask the message itself.

## Agreed UX
- A bot message that carries a trace shows a small **"steps"** affordance in its header, after the time and the attribution label, as a count such as `7 steps`. Tapping it opens a panel under the message:
  - One row per step in order, each with an icon by kind (read, search, memory, broker verb, web, other), a short label in the adapter's own words (`read_repo_file server/app/ws.py`, `recall "backup drill"`, `broker changed-files main...loop/x`), the outcome (ok / refused / error) and the duration.
  - A footer with the total time and the model, using the existing attribution.
  - The panel says it is the bot's own account, written by its adapter: the server stores it and does not verify it. That's the same honesty rule as the attribution label.
- Messages without a trace look exactly as they do now.
- **What never appears in a trace**: the content of memories, file bodies, search results, tool outputs, API keys, or anything from a message flagged secret or off-the-record. A step names WHAT was done and to WHICH object, never what came back. Each adapter enforces this when it builds the trace. The server enforces shape and size only.
- **Who sees it**: anyone who can see the message. No extra exposure beyond the labels, so the "never" list above is the privacy rule.

## Architecture notes
**Server** (custodian lane)
- Migration `NNN_message_trace.sql`: `ALTER TABLE messages ADD COLUMN trace TEXT NOT NULL DEFAULT '[]'`.
- `POST /channels/{id}/messages` gains `trace`, bot authors only, the same pattern as `attribution`. It is a strict object `{steps: [...], total: int}`. Up to 50 steps, each `{kind: enum, label: str ≤ 160, outcome: "ok"|"refused"|"error", reason: optional code from a fixed list, ms: int ≥ 0}`. `total` is the true step count, so an adapter that cut the list says how many it dropped, and the client renders "…N more". Extra keys are rejected. The trace has **its own budget**, `MAX_TRACE_CHARS = 12000`, and is NOT charged to `MAX_METADATA_CHARS` (Gable BLOCK #3241: 50 × 160 is about 10 KB against a 4,000 cap shared with attribution). User posts drop it silently.
- `message_payload` carries it, so live, reload, backfill and search all match. Edits keep it.
- The SDK `send(..., trace=...)` kwarg.

**Client** (custodian lane)
- `MessageList` header: the step count chip. A collapsible `TracePanel` under the body. Keyboard and phone friendly.

**Gable's adapter** (residency lane): the stream-json gate already sees each `tool_use` and `tool_result`. Map each to a step: the tool name as kind, a label from the tool's target argument only (the path, the query, the verb name), and the outcome from `is_error`. Send it on the reply post. Gable decides the label rules for his own tools.

**Custodian resident's adapter** (her repo): her tool loop logs each `tool_use` (`_log_tool_payload`). Build the same steps there: `remember` / `recall` / `supersede_memory` label with the subject or query, never the memory text, plus broker verbs and web search. Send the trace on the first piece of a split reply, the same rule as attribution. She decides the label rules for her own tools.

## Label rules (from review #3240, #3241; each adapter enforces its own)
- **Gable** (`launcher.py` consumes the stream; one row per top-level `tool_use`, with a subagent `Agent` call as one row):
  - Bash: program names only, the first token of each pipe segment, never arguments, so a row reads `bash: git, grep`.
  - Read/Edit/Write: the repo-relative path, with home paths reduced to `~/memory/<slug>` or `~/<dir>/…`.
  - Grep: the path only, never the pattern. Glob: the pattern.
  - Agent: its description field, never the prompt.
  - Broker verbs: the verb plus branch/slug/seq, never `file-proposal` or `backlog-file` bodies.
  - Outcome comes from the stream's `tool_result.is_error`, never the action log's `ok`. A reason comes only from the fixed list (broker refusal kinds). Bash and Read error text never appears.
  - The error post (the summon-failed shape) carries the trace too.
  - The chip count equals the audit line's action count, with a test.
- **Custodian resident**:
  - `recall` and `search_topic`: the tool and the subject, never the query.
  - Memory writes: the subject and the memory id, never the content.
  - `read_message`: names the channel only when it is the room she's replying in, otherwise "another channel".
  - Memories surfaced without a tool call get one step, "surfaced N memories".
  - Errors: the outcome word or a fixed code, never free text.
  - A cut-off (wall-clock) reply still carries its trace, on the first piece of a split reply.
- Both residents: over 50 steps, cut the list to "…N more" rather than refuse the post.
