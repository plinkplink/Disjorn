## Problem
An apps-builder turn writes `/work`, and `/work` is `/srv/apps/<app-id>` mounted rw (`run-apps.sh:156`). The app's repository lives at `/srv/apps/<app-id>/.git`, inside that mount, so the turn — the party this design models as possibly prompt-injected — writes the repository's own metadata, and every host-side git command reads it afterwards. In prod since stage 2 slice (i). Three vectors, all probed by me on git 2.47.3 (#2546, #2557):

1. **Host code execution as `res-appsbuilding`, outside the container.** A repo-local `core.fsmonitor=<cmd>` in `.git/config` ran under the harvest's own `git -c core.hooksPath=/dev/null -C <repo> add -A` (`apps_harvest.py:182`, inside the transient unit on the host). `hooksPath=/dev/null` closes hooks and nothing else; `filter.*.clean` (fires on `add`), `core.sshCommand`, `uploadpack.packObjectsHook`, `diff.*.textconv` are the same door. Blocklisting keys is the wrong shape: the list is git's to extend.
2. **Cross-app history read.** A real `.git` directory (passes stage 3's `_is_a_real_repo`) with a turn-written `objects/info/alternates` naming app B's object store plus a symlinked `refs/heads/<branch>` or `packed-refs` makes `remix`'s `clone --no-local` yield B's files and history. Needs only B's app id. The leak is in upload-pack on the parent; the child carrying no alternates proves nothing.
3. **The pointer file.** `.git` as a 40-byte `gitdir:` file. Closed for remix at `4573c4a`; `apps_harvest.ensure_repo` (`apps_harvest.py:215`) still decides "already a repo" by `.exists()` and is open.

Each fold so far closed a shape. The class is: we validate a path the adversary writes. The fix is that the adversary stops being able to write it.

## Agreed UX
None visible. Turns, previews, Live, Revert and Remix behave as today. A turn that writes a `.git` entry into `/work` now has it quarantined and named in `result.json`; nothing else a user sees changes.

## Architecture notes (D-series; each sentence is strikeable at review)

- **D1 — a host-only git root.** `/srv/apps-git/`, `0750 res-appsbuilding`, created by `10-appsbuilding.sh` beside the four existing roots (`10-appsbuilding.sh:240-246`). Per app: `/srv/apps-git/<app-id>.git/`, `0700`. `/srv/apps/<app-id>` stays the work tree and the only persistent rw mount. Nothing under `/srv/apps-git` is mounted into any container, ever; the podman argv in `run-apps.sh` is pinned by a test asserting no `-v`/`--mount` source resolves under it. The launcher gains the constant `GIT_ROOT` beside `APPS_ROOT` (`disjorn-apps-launch:165`) and sets `APPS_GIT_ROOT` for the wrapper; the wrapper passes `git_dir` in the harvest's JSON spec.
- **D2 — every git invocation names both trees explicitly, twice.** `apps_harvest.git` / `git_bytes` and the launcher's `_git` build `git --git-dir=<G> --work-tree=<W> -c core.hooksPath=/dev/null …` **and** set `GIT_DIR=<G>` / `GIT_WORK_TREE=<W>` in the per-call env dict. Flags are the statement; the env is the belt: measured on git 2.47.3 (`~/specs-drafts/probe-gitdir-env.py`), a flagless `git status` with cwd in `W` reads a turn-written `.git` pointer and follows it, while the same call with `GIT_DIR`/`GIT_WORK_TREE` in the env binds to `G` and never reads the entry. No path the turn can write is consulted to find the repository. The harvest's env gains `GIT_CONFIG_GLOBAL=/dev/null` (the launcher's `_git` already sets it, `disjorn-apps-launch:976`; the harvest sets only `NOSYSTEM` and must not be the weaker of the two). **Not taken, deliberately**: `GIT_CEILING_DIRECTORIES` and `GIT_DISCOVERY_ACROSS_FILESYSTEM=0` (in #2570's D2). Measured: with the ceiling set to `W`'s parent, a flagless call in `W` still reads `W/.git` first — the ceiling bounds the *upward* walk, and the entry we fear is at the cwd, below any ceiling. They cover nothing this spec is about; the env pin and test 4's grep pin cover the forgotten-flag case.
- **D3 — `ensure_repo` creates a split repo.** End state, pinned by test: `G` exists and holds `HEAD`; `core.bare=false`; `core.worktree` unset (the work tree is argv, never config); **no `.git` entry of any kind in `W`**. Measured (`probe-stray-git.py`): `git --git-dir=G --work-tree=W init` writes no entry into `W` **but does write `core.worktree=W` into `G/config`** — the earlier draft of this sentence said "unset" as if init left it so; it does not, and `ensure_repo` unsets it in the same function (`git --git-dir=G config --unset core.worktree`, measured to leave it absent). `--separate-git-dir` is not used: it writes a `.git` pointer file into `W`, exactly the entry this spec forbids. "Already a repo?" becomes "does `G/HEAD` exist" — a fact about the host-only tree. **`G` present but not a repo is a refusal, never a re-init**: `G` is written by host code only, so `G` existing as a symlink, a file, a directory not under the realpath of `/srv/apps-git`, or a directory without `HEAD` is an interrupted init or migration — an incident, not an input. `ensure_repo` raises, `run-apps.sh` does not start the container, the turn ends `failed` with the reason `gitdir_incomplete: <G>` in `result.json`, and nothing under `G` or `W` is written or deleted. The keyboard decides what the half-made `G` was. (Re-init over a directory that might hold objects is the branch that loses history; it is not written.)
- **D4 — remix reads the host-only tree.** `_is_a_real_repo` is deleted, not kept — there is nothing left in `W` to validate. Its replacement checks `G`: real directory by lstat, realpath under `/srv/apps-git`, holds `HEAD`; in both `preflight_remix` (root) and `remix_app` (seat). Clone stays `--no-local --no-hardlinks` (two separately-writable apps must share no object file, alternates or not), and its source is `G`, not `W`. The child gets `/srv/apps-git/<child>.git` and a work tree with no `.git` entry; the lineage commit `remix of <parent>` is unchanged. Same trap as D3: `clone --separate-git-dir` writes the pointer file. One shape that does not: `clone --bare --no-local --no-hardlinks <parentG> <childG>`, then `core.bare=false`, then `git --git-dir=<childG> --work-tree=<childW> checkout -q`, then the D3 end-state check. Builder's pick; test 6 pins the end state, not the invocation.
- **D5 — a `.git` entry in `/work` is a stray, quarantined as a class.** **Measured 2026-09-13 on git 2.47.3** (`~/specs-drafts/probe-stray-git.py`, output in #custodian): in a split work tree, a top-level `W/.git` as a real directory, as a symlink to a directory, and as a `gitdir:` pointer file is listed by none of `status --porcelain -uall --ignored=matching`, `add -A`, `ls-files`, or `clean -ffdxn`; `real.txt` beside it is listed normally. A nested `sub/.git/` is likewise never listed by `status`/`add`/`ls-files`; `clean -ffdxn` names `sub/` whole only because `sub/` is an untracked directory, and `reset_tree`'s single-`f` `clean -fdx` (`apps_harvest.py:462`) refuses a directory holding `.git` — so today's reset leaves a nested stray standing too. With `--git-dir` explicit, `rev-parse --git-dir` answers `G` whatever `W/.git` says. So a turn-written `.git` — file, dir or symlink, top-level or nested — is invisible to every porcelain the harvest drives, including the scan, and rsync's `--exclude .git` keeps it out of the preview. Invisible is not harmless: it is the one place in the tree a payload sits unscanned across turns. So the harvest, before the scan, lstat-walks `W` for entries named `.git`, moves each to `<quarantine>/<app>/<turn>/stray-git/<relpath>` (never followed), and records `stray_git: [paths]` in `result.json`; the turn otherwise proceeds normally. The watcher's `_changed_since` stops skipping `.git` (its reason — `git init` touching `W/.git` at t=0 — no longer exists). `preview_argv`'s `--exclude .git` stays. This replaces #2570's D5; `git clean -ff` is not taken, because git never lists a `.git` entry for `clean` to remove.
- **D6 — one-time migration**, `harness/keyboard/11-apps-gitdir-migrate.sh`, root, idempotent, refuses while any `disjorn-apps-*` unit is active. Per `/srv/apps/<id>`:
  1. **Audit first, printed, before anything moves**: for each existing `.git/config`, every key outside the set `core.{repositoryformatversion,filemode,bare,logallrefupdates}`, `user.*`, `init.*` is printed verbatim; non-sample files under `hooks/`; `objects/info/alternates` contents; every symlink anywhere under `.git` (`find -type l`). One block per app to the keyboard, kept in the merge record. "Was this hole used?" is answerable today and not after the rewrite.
  2. `.git` not a real directory (pointer file, symlink): not followed. Moved to `/srv/apps-quarantine/<id>/gitdir-migration/`; fresh `G` init'd per D3; first commit `history discarded at migration: .git was a pointer`.
  3. `.git` a real directory with any symlink anywhere under it: quarantined whole, same as 2.
  4. Otherwise: `mv .git /srv/apps-git/<id>.git`, then **sanitize by ALLOWLIST before any git command touches it** (rev 3, Gable #2604 — rev 2 removed three named things, which is the blocklist shape this spec calls wrong, and a one-line `commondir` was outside it): keep exactly `HEAD`, `refs/`, `packed-refs`, `objects/` minus `objects/info/`; `config` deleted and rewritten minimal (format version, `core.bare=false`, `user.name`, `user.email`); **every other top-level entry deleted by name** (`hooks/`, `info/`, `logs/`, `worktrees/`, `commondir`, `gitdir`, `index`, and whatever git grows a name for next); the audit prints, before anything moves, every top-level entry git itself would not have written — a list deliberately WIDER than the allowlist, since the entries git does write (`config`, `hooks/`, `info/`, `logs/`, `index`) are deleted at the move too and are audited by the config / hooks / alternates lines instead of being reprinted as an anomaly for every honest app — with `commondir`/`gitdir` shown with their contents. Then `git --git-dir=G fsck --no-dangling` (fsck reads config, so it runs after the rewrite); an fsck failure quarantines whole and re-inits, printed. After a clean fsck the index is rebuilt with `read-tree HEAD` when there are commits, so the next `add -A` diffs against the tree rather than against nothing. `fresh_repo` sweeps every nested `.git` in W (dir, symlink or pointer) before its base `add -A`, so no gitlink lands in the base commit. The script refuses to start unless the installed harvest carries the `refuse` mode — the old CLI's `ensure-repo` would `init` inside G before the commit died.
  5. Result: `G` `0700 res-appsbuilding`, `W` with no `.git` entry, `W` mode `0750` unchanged. Apps with no `.git` at all are left alone; their first turn creates `G`.
- **D7 — the wall, written once.** A paragraph in `run-apps.sh`'s header and `apps_harvest`'s docstring: the turn's writable surface is the work tree only; git metadata is host-only by location; a shape check on a path the turn can write is not a boundary and is never written down as one (the `gate.py` #2561 discipline). Work-tree files that name git machinery (`.gitattributes` filters, `.gitmodules`) reference drivers the host-only config never defines, and stay inert for that reason, not by a scan.

## Tests
Acceptance is not "fsmonitor is blocked". It is: **a turn writes `.git` and the write lands nowhere the host git ever reads.** Each new test reverted-and-rerun red against pre-fold code before it counts.

1. Plant `W/.git/config` with `core.fsmonitor` naming a marker script; full harvest; marker never runs; the turn's real content commits normally; `stray_git` names the entry and it sits in quarantine.
2. Plant `W/.git` as a real directory with `objects/info/alternates` naming app B's `G` plus a symlinked ref; remix yields the parent's own history only; B's objects absent from the child (object-id set difference, not "no alternates file").
3. Plant `W/.git` as a `gitdir:` pointer at another app's `G`; `ensure_repo`, harvest and remix ignore it (nothing refuses by shape, because nothing looks); `ensure_repo` is a no-op decided on `G/HEAD`.
4. Argv and env pins: the harvest's and launcher's git argv carry `--git-dir` and `--work-tree` and their env carries `GIT_DIR`, `GIT_WORK_TREE`, `GIT_CONFIG_GLOBAL=/dev/null`; the podman argv mounts nothing under the git root. **Grep pin** (Claudette #2587): over `harness/` excluding `tests/`, every `subprocess` argv whose first element is a git binary sits inside `apps_harvest.git`, `apps_harvest.git_bytes`, or the launcher's `_git`, and no shell file under `harness/cc/apps` or `harness/keyboard` runs `git` without `--git-dir` except `11-apps-gitdir-migrate.sh`'s audit lines, which read a `.git` that has not moved yet and are listed by name in the test. Today's three call sites are the ones D2 fixes; the pin is what stops a fourth being written next month.
5. `ensure_repo` on a fresh app creates `G` and no `.git` entry in `W`, and `git --git-dir=G config core.worktree` exits 1; second call creates nothing. 5b. `G` exists as an empty directory: raises `gitdir_incomplete`, `G` still empty afterwards, `W` untouched, no `init` in the argv log. 5c. `G` exists as a symlink to a real repo, or as a file: same refusal, target unread.
6. Remix: child `W` has no `.git`; child history = parent's + lineage commit; parent and child share no object file (inode comparison).
7. Migration on a fixture tree: pointer-file app quarantined + re-init'd; symlink-inside-git app quarantined whole; honest app moved and sanitized (config minimal, hooks gone, alternates gone), history intact; second run a no-op; refuses with an active unit; audit block printed for each.
